# 0019 — daily-trade-tracker: consuming a private artifact without owning it

**Status:** accepted, 2026-09-23

## Context

[`thetaskmaster42/tools`](https://github.com/thetaskmaster42/tools) is a private
monorepo of homelab utilities. The first is **daily-trade-tracker** — FastAPI +
SQLAlchemy + a small static frontend — published as
`ghcr.io/thetaskmaster42/daily-trade-tracker`.

The constraint that shapes everything: **this repo does not modify `tools`.** It
consumes the published image and works around whatever that image does. The
`gitops/` tree that used to live in `tools` is removed; this repo is the only
place that describes what is deployed.

That `gitops/` tree could not have been used as it stood. It was an
**app-of-apps** (`argocd-apps.yaml` → `gitops/argocd/`), which
[ADR 0001](0001-applicationset-not-app-of-apps.md) rejected outright; it used
`project: default`, bypassing the `infra`/`apps` AppProjects; it omitted the
`resources-finalizer.argocd.argoproj.io` finalizer, so deleting it would have
orphaned the workloads; it pinned `:latest`; and it carried a `Secret` with a
plaintext `DATABASE_URL`, which is survivable in a private repo and a credential
leak the moment it lands in this public one.

## Decision

A normal entry under `apps/`, generated by `appset-apps` like everything else,
with the manifests written locally.

**Local manifests are forced, not preferred.** prep-tracker pulls its `k8s/`
directory from `raw.githubusercontent.com` pinned to a commit sha, and that is
the nicer pattern — but ArgoCD's repo-server cannot authenticate to raw URLs, so
it is unavailable for a private source. This is the draw.io shape instead:
manifests here, `sourceRepo` as an annotation pointing upstream.

## The four things that would have broken it

### 1. Arch — closed upstream, and the package was renamed

At first review the image published `linux/amd64` only: an instant
`exec format error` on every node here. Upstream now sets
`platforms: linux/amd64,linux/arm64` and its CI tests on both architectures plus
a real Postgres 16, so the gate is genuinely closed — re-verified against the
registry rather than read off the workflow.

The package was also **renamed**: `daily-trade-tracker` →
`tool-packages-daily-trade-tracker`. The old name still exists in GHCR with its
stale, partly amd64-only tags, so a typo pulls a real but abandoned image instead
of failing loudly.

| Tag (new package) | Arches |
|---|---|
| `sha-e667131` | `linux/amd64`, `linux/arm64` |
| `sha-1b91a17` | `linux/amd64`, **`linux/arm64`** ← pinned, = HEAD of main |
| `latest` | same digest as `sha-1b91a17` |

**Re-check the arch of any new tag before bumping it** — nothing in this repo's CI
can validate an image it has not been told about.

### 2. CloudNativePG's `uri` key cannot be used

This is the subtle one. CNPG helpfully publishes a ready-made `uri`, and it is
wrong for this app:

- `uri` uses the scheme `postgresql://`
- SQLAlchemy 2.0 resolves that to the **psycopg2** driver
- the image installs `psycopg[binary]` — psycopg **3** — and nothing else

The result is `ModuleNotFoundError: No module named 'psycopg2'` at import, which
reads as a broken image rather than a wrong connection string.

So the URL is composed in the pod spec from the Secret's component keys with an
explicit dialect, relying on Kubernetes expanding `$(VAR)` from earlier env
entries:

```
postgresql+psycopg://$(DB_USER):$(DB_PASSWORD)@$(DB_HOST):$(DB_PORT)/$(DB_NAME)
```

This is only safe because CNPG generates a 64-character password from a URL-safe
alphabet — verified across all four CNPG clusters here, none requiring
percent-encoding. A generated password containing `@` or `/` would silently
corrupt the URL, so that assumption is the fragile part of this design and is
commented as such at the point of use.

The payoff is keeping the operator-generated credential: no database password in
the bootstrap bundle, which is what [ADR 0014](0014-sops-as-the-only-secret-manager.md)
calls the preferred shape.

### 3. The image's user is a name, so `runAsUser` is mandatory

The Dockerfile ends `USER appuser`. With `runAsNonRoot: true` and no explicit
`runAsUser`, the kubelet refuses to start the container at all:
*"container has runAsNonRoot and image has non-numeric user (appuser), cannot
verify user is non-root."*

`appuser` is uid 1000, gid 1000 — read out of the image's own layer rather than
inferred from `useradd` defaults. `/data` inside the image is already owned by
uid 1000, which matters because `app/db.py` calls `DATA_DIR.mkdir(exist_ok=True)`
at import **even on Postgres**. It is a no-op, but `readOnlyRootFilesystem: true`
would fail it and crash the app before FastAPI starts.

### 4. The SQLite fallback is a data-loss trap, disarmed by always setting the URL

`app/db.py` defaults to `sqlite:///$DATA_DIR/trades.db` when `DATABASE_URL` is
unset. SQLite is the source repo's **local-testing** path; in this cluster
Postgres is the only store. Nothing mounts a volume at `/data`, so if that
fallback ever engaged the app would write a database to the container's
ephemeral layer and lose it on the next restart, silently — in a cluster that
currently restarts every pod several times a day.

It cannot engage as configured: the five `secretKeyRef` entries mean a missing
Secret is `CreateContainerConfigError`, and a missing env var leaves a literal
`$(DB_PASSWORD)` in the URL, which fails to connect. Both are loud. **Do not add
a `/data` volume** — it would turn a loud failure into a quiet one.

## The health endpoint became database-dependent

`/healthz` used to return a static `{"status": "ok"}`. It now executes
`SELECT 1` and returns 500 when the database is unreachable, and upstream's
README states the intent: *"so k8s restarts the app pod if its Postgres dies."*

That is right for readiness and wrong for liveness. Restarting the application
does not repair its database, and on this cluster k3s-server blackholes several
times a day — taking the API server and every Postgres pod with it. A
DB-dependent liveness probe converts each of those outages into an app restart
storm that cannot help.

So readiness uses `/healthz` (stop serving while the database is gone) and
liveness uses `GET /`, which returns a static `index.html` with no database
access. Liveness answers "is the process wedged", which is the only question it
should ask.

Schema creation also gained a retry — `_ensure_schema()` tries for 15 × 2s and
then **raises**. Thirty seconds is short for a cold CNPG start on NFS, so the
sync-wave ordering is still doing real work: without it, the first deploy would
crashloop its way to readiness instead of waiting.

## Tailnet only, and not for the usual reason

**This application has no authentication of any kind.** Unauthenticated
`POST /trades`, `PUT /trades/{id}` and `DELETE /trades/{id}` — no login, no
session, no API key. Anyone who can reach it can rewrite or delete the journal.

So it gets no LAN Ingress, on the same reasoning that keeps headlamp off the LAN
plane. Authentication upstream is the prerequisite for a LAN name, not a Traefik
annotation.

## "The DB runs on the NAS"

Satisfied by the storage class, not by a hand-built Postgres. CloudNativePG runs
the engine in-cluster; the data lives on `nfs`, which is `portal`
(192.168.11.3) today and the TrueNAS box later. Relocating it is then a storage
migration with no application change — the class name does not move.

## What this gives up

- **Rolling updates.** One replica and `Recreate`, because `create_all()` runs at
  import. Seconds of downtime per image bump.
- **A pull secret to rotate.** A fine-grained PAT with package read-only, in the
  bootstrap bundle. On expiry the symptom is `ImagePullBackOff: unauthorized`
  against a Deployment that otherwise looks fine. Making the *package* public —
  the image holds no secrets — would remove this entirely and keep the source
  private.
- **No schema migrations.** `create_all()` creates missing tables and does
  nothing else; the in-app upgrade helper early-returns on anything that is not
  SQLite. The first column change to an existing table will need handling
  upstream.
