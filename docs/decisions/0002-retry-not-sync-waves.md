# 0002 — Convergence by retry, not by sync waves

**Status:** accepted, 2026-08-17

## Context

Several infra services have real dependencies: `metallb-config`'s
`IPAddressPool` needs MetalLB's CRDs; Traefik needs a MetalLB pool to get its
VIP; cert-manager's `ClusterIssuer` needs cert-manager's CRDs.

The obvious mechanism is `argocd.argoproj.io/sync-wave`, and an early draft of
this design put a `wave:` field in each `service.yaml`.

## The correction

**That would have been inert.** Sync waves order resources *within a single
Application's sync operation*. They do not order separate Application CRs
relative to each other. Applications generated by an ApplicationSet have no
parent sync operation to sequence them — each syncs independently — so a
`sync-wave` annotation on them does nothing.

(In an app-of-apps layout the waves would at least stagger *creation*, because
the child Applications are resources of the parent. Even there it would only
order creation, not readiness.)

## Decision

Order-dependent Applications carry:

```yaml
retry:
  limit: -1
  backoff: { duration: 30s, maxDuration: 5m }
```

and simply fail until their prerequisite exists, then succeed.

## Consequences

- The dependency graph is never declared anywhere. This is a feature: there is
  no ordering metadata to get out of sync with reality.
- Convergence is eventual. A fresh cluster shows failing Applications for the
  first minute or two, which is expected and not a signal to intervene.
- It is order-independent, so a nuke-and-rebuild works regardless of the sequence
  in which ArgoCD happens to process things — which matters, because rebuilding
  is a routine operation here.
